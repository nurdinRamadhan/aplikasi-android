SECURITY WHITEPAPER & CRYPTOGRAPHIC PROTOCOL

Produk: Al-Hasanah Media Android dan Supabase Backend

Versi dokumen: 2.0 Production Alignment

Tanggal: 23 Mei 2026

Lingkup: aplikasi Android wali santri, alumni, donasi/infaq, pembayaran, dompet santri, notifikasi, chat alumni, database Supabase, Edge Functions, cron, dan audit operasional.

Pernyataan akurasi: dokumen ini menggantikan narasi lama yang terlalu sempit pada "Tabungan Santri" dan terlalu absolut pada istilah "zero trust". Sistem ini menggunakan pendekatan defense-in-depth, least privilege, RLS-first, cryptographic control, auditability, dan fail-safe operation. Dokumen ini hanya menyatakan kontrol yang ditemukan dalam implementasi Android, migrasi database, Edge Functions, dan konfigurasi rilis saat ini.

1. Ringkasan Eksekutif

Al-Hasanah Media adalah aplikasi Android monitoring wali santri dengan backend Supabase. Aplikasi ini menggabungkan data santri, aktivitas akademik dan kepesantrenan, pembayaran SPP, donasi/infaq, dompet santri, jadwal ibadah, Al-Qur'an digital, forum dan chat alumni, tanya AI, cuaca, notifikasi, serta fitur offline-first untuk modul non-keuangan.

Keamanan sistem dibangun dalam beberapa lapisan:

  • Identitas dan sesi: Supabase Auth, JWT session, pemetaan role pada profiles, serta pembatasan akses berdasarkan auth.uid().
  • Database access control: Row Level Security aktif pada hampir seluruh tabel aplikasi publik dan seluruh tabel operasional ops.
  • Fungsi backend terkontrol: operasi sensitif dijalankan melalui RPC/Edge Functions dengan SECURITY DEFINER, role check, revocation grants, dan service-role boundary.
  • Kriptografi Android: AndroidKeyStore, AES-GCM, Ed25519, Argon2id, ECDH, ECDSA, PBKDF2, HMAC-SHA256, dan SHA-256 sesuai kebutuhan modul.
  • Keuangan online-first: pembayaran, dompet santri, top up, settlement, dan transaksi kantin tetap online agar ledger, status, risk rule, dan audit selalu berasal dari backend.
  • Offline-first terkendali: modul non-keuangan memakai cache lokal dengan TTL dan enkripsi untuk data yang sensitif.
  • Notifikasi aman: FCM token diikat ke user login, invalid token dapat dinonaktifkan, payload chat disanitasi, dan antrean notifikasi diarsipkan otomatis.
  • Audit dan operasional: audit log, finance immutable audit trail, wallet audit, reconciliation, hash-chain verification, incident playbook, backend health snapshot, dan cron maintenance.

2. Prinsip Keamanan

2.1 Defense-in-Depth

Tidak ada satu kontrol tunggal yang dianggap cukup. Android, Edge Function, database, RLS, cron, audit log, dan notification worker saling menutup kelemahan satu sama lain.

2.2 Least Privilege

Client Android menggunakan publishable/anon key dan session user. Service role hanya digunakan pada lingkungan backend/Edge Function untuk operasi yang memang harus melewati RLS, misalnya webhook Midtrans, push notification worker, settlement service, reconciliation, dan audit otomatis.

2.3 RLS-First

Data aplikasi tidak dianggap aman hanya karena UI tidak menampilkan menu tertentu. Tabel seperti santri, tagihan_santri, transaksi_keuangan, notification_queue, chat_messages, dompet_santri, transaksi_dompet, dan tabel wallet lain dikunci dengan Row Level Security.

2.4 Online Authority untuk Keuangan

Modul finansial sengaja tidak dibuat offline-first penuh. Tagihan SPP, pembayaran, donasi/infaq, dompet santri, top up, kantin, settlement, dan status pembayaran harus tetap diverifikasi oleh backend agar tidak terjadi double spend, saldo lokal palsu, atau status pembayaran yang tidak sinkron.

2.5 No Plaintext untuk Chat E2EE

Chat alumni memakai placeholder server seperti "Pesan terenkripsi". Isi pesan terenkripsi disimpan per perangkat penerima, sehingga database tidak menyimpan isi percakapan dalam plaintext untuk skema baru e2ee_v1.

4. Identitas, Role, dan Session Boundary

Identitas utama memakai Supabase Auth. Database memakai auth.uid() untuk menghubungkan user dengan profil, wali santri, alumni, admin, bendahara, dewan, rois, kantin, dan service process.

Role aplikasi disimpan pada public.profiles.role. Fungsi helper seperti is_admin_in_roles, access scope, dan fungsi privat pada app_private digunakan untuk memisahkan hak baca/tulis antar role.

Untuk wali santri, pola akses utama adalah relasi santri.wali_id = auth.uid(). Ini memastikan wali hanya melihat data anak yang terhubung dengan akunnya. Untuk alumni, akses forum/chat bergantung pada status alumni aktif dan partisipasi percakapan.

5. Database Security dan RLS

5.1 Status RLS

Audit database saat dokumen ini dibuat menunjukkan RLS aktif pada tabel aplikasi utama, termasuk profiles, santri, tagihan_santri, transaksi_keuangan, notification_queue, rag_documents, forum_threads, chat_*, dompet_santri, wallet_*, dan tabel ops.

Skema ops dipakai untuk data operasional internal seperti finance_audit_events, notification_archive, backend_health_snapshots, incident_playbooks, dan midtrans_reconciliation_queue. Banyak tabel ops sengaja RLS enabled tanpa policy publik agar tidak bisa dibaca oleh client biasa.

5.2 Grant Tightening

Migrasi produksi telah melakukan tightening pada grant sensitif, termasuk pencabutan akses langsung pada beberapa tabel dan fungsi dari anon/authenticated, lalu menggantinya dengan RPC yang memvalidasi user, role, dan relasi bisnis. Operasi seperti settlement merchant, wallet system freeze, wallet reconciliation, wallet security audit, dan fungsi internal lain diberikan ke service_role.

5.3 SECURITY DEFINER

SECURITY DEFINER digunakan untuk kasus yang memerlukan akses terkontrol melampaui RLS biasa. Implementasi yang baik pada sistem ini mencakup:

  • set search_path eksplisit untuk mengurangi risiko function hijacking.
  • Role check di dalam fungsi.
  • Revocation dari public, anon, dan/atau authenticated bila fungsi hanya boleh dipanggil service.
  • Audit log ketika fungsi sensitif dijalankan.

6. Android Security

6.1 AndroidKeyStore

Aplikasi memakai AndroidKeyStore sebagai root of trust lokal untuk beberapa kunci AES-GCM:

  • alhasanah_santri_detail_cache_v1 untuk enkripsi cache detail santri.
  • alhasanah_alumni_chat_cache_v1 untuk enkripsi cache alumni/chat.
  • alhasanah_chat_outbox_v1 untuk outbox chat lokal.
  • wallet-device-wrap-key untuk membungkus private key wallet yang disimpan lokal.
  • Alias per user/per device untuk membungkus private key chat E2EE.

6.2 Network Security Config

Aplikasi menonaktifkan cleartext traffic secara global dengan cleartextTrafficPermitted=false. Domain Supabase dan Midtrans memiliki certificate pin-set sampai 31 Desember 2027. Pinning yang terpasang:

  • sldobkbolvrahlnowrga.supabase.co
  • api.sandbox.midtrans.com
  • api.midtrans.com

Konsekuensi operasional: sebelum sertifikat/chain provider berubah atau mendekati kedaluwarsa, pin harus diuji dan diperbarui agar aplikasi release tidak gagal koneksi.

6.3 Root dan Emulator Guard

Pada build release, operasi dompet sensitif menjalankan guard terhadap indikasi root dan emulator. Guard ini memblokir transaksi bila ditemukan path su, aplikasi superuser/Magisk tertentu, test-keys, atau fingerprint/model emulator. Pada build debug guard dilewati agar pengembangan tetap praktis.

7. Offline-First dan Local Data Protection

Offline-first digunakan untuk pengalaman baca yang cepat dan tetap berguna saat jaringan lemah. Modul seperti data santri, aktivitas santri, jadwal sholat, kalender Islam, hadis, panduan ibadah, kitab, alumni, forum, dan chat memiliki cache lokal dengan TTL.

TTL yang ditemukan antara lain:

  • Lokasi jadwal sholat: 30 hari.
  • Jadwal sholat harian: 48 jam.
  • Jadwal sholat bulanan: 40 hari.
  • Hadis daftar: 90 hari; detail hadis: 180 hari.
  • Panduan ibadah: 90-180 hari.
  • Kalender Islam: 36 jam; hari libur: 30 hari.
  • Cache alumni: akses 15 menit, direktori 5 menit, forum 45 menit, chat 24 jam.

Data lokal sensitif dienkripsi dengan AES/GCM/NoPadding dan kunci dari AndroidKeyStore. Modul keuangan tidak mengandalkan cache offline sebagai sumber kebenaran.

8. Cryptographic Protocol: Alumni Chat E2EE

8.1 Key Establishment

Setiap perangkat chat memiliki key pair EC pada kurva secp256r1. Public key perangkat disinkronkan ke backend, sedangkan private key disimpan lokal setelah dibungkus dengan AES-GCM dari AndroidKeyStore.

Untuk mengenkripsi pesan ke perangkat penerima, aplikasi melakukan ECDH antara private key pengirim dan public key perangkat penerima. Shared secret kemudian di-hash SHA-256 untuk membentuk AES key.

8.2 Message Encryption

Isi pesan dienkripsi memakai AES/GCM/NoPadding dengan nonce 12 byte dan tag 128 bit. AAD berisi kombinasi user/perangkat penerima dan perangkat pengirim, sehingga ciphertext terikat pada konteks percakapan perangkat.

Server menyimpan metadata pesan, placeholder, dan ciphertext per device pada chat_message_device_ciphertexts. Isi plaintext tidak disimpan sebagai chat_messages.content untuk skema e2ee_v1.

8.3 Plaintext Redaction

Migrasi harden_alumni_chat_e2ee, drop_chat_message_plaintext_content, dan enforce_chat_zero_plaintext_surfaces mengubah pesan lama menjadi placeholder, memaksa content = 'Pesan terenkripsi', dan menyamarkan preview notifikasi. Admin monitor hanya melihat statistik dan preview terenkripsi, bukan isi pesan.

8.4 Key Backup

Backup private key chat memakai PBKDF2WithHmacSHA256 dengan 210.000 iterasi, salt 16 byte, AES-GCM, dan verifikasi pasangan kunci melalui tanda tangan SHA256withECDSA sebelum restore diterima.

9. Cryptographic Protocol: Dompet Santri

9.1 Device Signature

Wallet device crypto memakai key pair Ed25519. Private key disimpan lokal dalam SharedPreferences setelah dienkripsi AES-GCM dengan key dari AndroidKeyStore. Public key dikirim ke backend untuk registrasi perangkat.

Operasi seperti kantin authorization dan card lookup menandatangani canonical message yang berisi versi protokol, wallet public id, nominal, kantin user id, Android device id, idempotency key, media, merchant/outlet id, dan nonce.

9.2 PIN Santri

PIN tidak disimpan plaintext. Aplikasi membuat verifier dengan Argon2id:

  • Salt: 16 byte random.
  • Memory default: 19.456 KiB.
  • Iterations: 3.
  • Parallelism: 1.
  • Output: 32 byte.

Database memiliki constraint yang mencegah verifier menyerupai PIN numeric plaintext. RPC wallet_set_student_pin_verifier memastikan actor adalah wali dari santri terkait sebelum menyimpan salt, verifier, KDF parameter, dan versi PIN.

9.3 PIN Proof

Untuk pembuktian PIN, aplikasi menurunkan verifier Argon2id dari input PIN, lalu membuat HMAC-SHA256 atas message tantangan. Material verifier di memori dihapus setelah dipakai.

9.4 QR/NFC Opaque Identifier

Kontrol wallet menyatakan qr_payload_policy = opaque_public_id_only. QR/NFC tidak boleh memuat saldo atau data sensitif. Payload hanya menjadi pointer publik yang harus diverifikasi ulang oleh backend.

10. Wallet Banking-Grade Controls

10.1 System Freeze

Tabel wallet_system_controls memiliki freeze switch untuk wallet_transactions. Bila rekonsiliasi internal gagal atau operator/service mendeteksi risiko kritis, transaksi dapat dibekukan secara sistemik.

10.2 Risk Rules

Risk detection wallet mencakup:

  • Jam operasional transaksi Asia/Jakarta, default 06:00-21:00.
  • Velocity santri 5 menit.
  • Velocity kantin 10 menit.
  • Nominal di atas baseline rata-rata harian.
  • Perangkat kantin belum aktif.
  • Public key perangkat kantin tidak cocok.

Action risk meliputi flag, require_parent_approval, block, freeze_wallet, dan freeze_system.

10.3 Idempotency dan Expiry

Authorization session wallet memakai idempotency key kuat, challenge, nonce, dan expiry sekitar 5 menit. Repeated request dengan idempotency key yang sama diperlakukan sebagai replay sah dan mengembalikan session yang sama, bukan membuat transaksi baru.

10.4 Ledger, Hash-Chain, dan Reconciliation

transaksi_dompet menjadi ledger utama. Sistem memiliki wallet_reconciliation_runs untuk membandingkan net ledger dengan saldo cache aktif, serta wallet_ledger_integrity_runs untuk verifikasi hash-chain. Jika ledger net dan saldo cache tidak cocok, sistem dapat memicu freeze otomatis.

10.5 Merchant dan Settlement

Ekosistem kantin memakai wallet_merchants, wallet_merchant_outlets, wallet_merchant_users, wallet_merchant_balances, wallet_merchant_ledger, dan wallet_merchant_settlement_requests. Settlement service dikunci agar operasi payout tidak dijalankan langsung oleh client biasa.

10.6 Dispute

wallet_disputes memungkinkan wali atau admin membuka sengketa atas transaksi ledger. RLS membatasi wali hanya melihat dispute milik santri yang terhubung dengannya, sementara admin role terkait dapat melakukan review.

11. Payment Security: SPP, Donasi/Infaq, dan Top Up

11.1 Midtrans Server Key Isolation

Midtrans server key tidak berada di aplikasi Android. Pembuatan charge/Snap dilakukan melalui Edge Functions seperti midtrans-core-charge, midtrans-snap, dan wallet-topup-create. Android hanya mengirim permintaan ke backend dan menerima instruksi pembayaran yang telah dinormalisasi.

11.2 Webhook Signature Verification

Webhook midtrans-payment memverifikasi signature_key menggunakan SHA-512 atas kombinasi order_id, status_code, gross_amount, dan server key. Jika signature tidak cocok, webhook ditolak.

11.3 Status Normalization

Status transaksi dari Midtrans dinormalisasi ke status aplikasi. Pembayaran sukses memperbarui transaksi_keuangan, tagihan_santri, atau wallet_payment_intents sesuai jenis order. Untuk top up wallet, webhook memposting ledger credit melalui RPC backend.

11.4 Public Payment Status

get_payment_status_public tersedia untuk mengecek status berdasarkan order id. Fungsi ini harus tetap mengembalikan data minimal dan tidak boleh membocorkan data wali/santri di luar konteks pembayaran.

12. Notifikasi dan FCM Security

12.1 Token Binding

FCM token didaftarkan melalui RPC register_my_fcm_device yang memakai user login aktif. Desain ini mencegah token lintas akun menyebabkan notifikasi nyasar. Token dapat dinonaktifkan melalui deactivate_my_fcm_device.

12.2 Push Worker

Notification worker berjalan melalui Edge Function push-notifications. Cron memanggil function tanpa JWT legacy; function memakai secret service role internal. Worker memproses antrean bertahap, mengirim FCM, dan memperbarui status.

12.3 Sanitasi Payload

Notifikasi chat tidak membawa plaintext pesan. Body memakai teks seperti "Pesan terenkripsi baru". Notifikasi aktivitas santri, prestasi, perizinan, kesehatan, pelanggaran, tagihan, donasi, dan dompet memakai bahasa ramah untuk wali santri dan menyertakan metadata navigasi secukupnya.

12.4 Retention dan Archive

Antrean aktif notification_queue dibersihkan otomatis oleh ops.archive_and_prune_notifications. Kebijakan default:

  • Notifikasi sent/read non-kritis diarsipkan setelah 30 hari.
  • Notifikasi failed non-kritis diarsipkan setelah 14 hari.
  • Notifikasi kritis diarsipkan setelah 90 hari jika sudah reviewed/resolved/ignored.

Data dipindahkan dulu ke ops.notification_archive, baru dihapus dari antrean publik. Job berjalan harian pukul 02:00 WIB.

13. Finance Audit Trail

Sistem memiliki immutable audit trail pada ops.finance_audit_events. Trigger mencatat perubahan penting pada transaksi_keuangan dan tagihan_santri, termasuk nominal, status, metode pembayaran, order id Midtrans, waktu sukses, admin pencatat, sisa tagihan, tanggal jatuh tempo, dan deskripsi tagihan.

Audit ini tidak mengubah workflow bisnis; ia hanya menambah jejak forensik agar perubahan finansial dapat ditelusuri.

14. AI/RAG Security

Fitur Tanya AI menggunakan dokumen RAG dan log query yang berada pada tabel RLS-enabled seperti rag_documents, rag_document_chunks, rag_query_logs, dan rag_rate_limits. Akses harus tetap mengikuti role dan konteks user. Rate limit dipakai untuk mengurangi penyalahgunaan.

Untuk audit/security AI wallet, sistem menyimpan hasil analisis pada wallet_security_ai_analyses dan audit deterministic pada wallet_security_audit_runs. Data yang dikirim ke analisis harus bersifat sanitized dan tidak membawa rahasia pembayaran atau PIN.

15. Operational Security

15.1 Cron dan Maintenance

Sistem memiliki job otomatis untuk push notification, reconciliation, ledger integrity, dispute SLA, weekly digest, backend health snapshot, maintenance digest, dan retention notifikasi. Job ini membantu mendeteksi kondisi rusak sebelum terlihat oleh user.

15.2 Incident dan Self-Healing

Skema ops menyimpan incident_playbooks, incidents, incident_events, backend_alerts, dan backend_health_snapshots. Data ini menjadi basis control tower untuk memantau masalah operasional seperti cron gagal, token FCM bermasalah, anomali Midtrans, dan kondisi backend lain.

15.3 Security Audit Center

wallet_run_security_audit melakukan pemeriksaan deterministic atas freeze switch, parent approval threshold, rekonsiliasi, hash-chain, risk event, dispute, notifikasi kritis, merchant assignment, saldo merchant, settlement, PIN, RLS, anon grants, QR opaque, Argon2id, dan cron. Hasilnya disimpan di wallet_security_audit_runs.

17. Known Advisories dan Residual Risk

Catatan penting: Supabase security advisor masih mendeteksi beberapa hal yang perlu dicatat sebagai residual risk atau pekerjaan hardening lanjutan. Dokumen ini tidak menyembunyikan temuan tersebut.

  • public.spatial_ref_sys masih RLS disabled. Tabel ini berasal dari PostGIS dan sering bersifat referensi geospasial, tetapi karena berada di schema publik exposed, advisor menandainya critical. Remediasi perlu hati-hati agar tidak merusak fitur geospasial.
  • Extension postgis berada di schema public. Advisor menyarankan memindahkan extension ke schema khusus.
  • Beberapa fungsi SECURITY DEFINER masih callable oleh anon atau authenticated. Sebagian memang disengaja sebagai public/signed-in RPC dengan validasi internal, namun daftar ini perlu review berkala.
  • Leaked password protection Supabase Auth masih terdeteksi disabled. Untuk produksi penuh, fitur ini sebaiknya diaktifkan jika kompatibel dengan kebijakan login.
  • Certificate pinning membutuhkan rotasi sebelum 31 Desember 2027 atau ketika provider mengganti certificate chain.
  • Device id berbasis Android ID cukup untuk binding operasional saat ini, tetapi bukan identitas hardware absolut. Keamanan utama tetap harus berasal dari user session, FCM token binding, public key device, signature, RLS, dan backend validation.
  • Jika user membagikan password, PIN, atau perangkat tidak terkunci, kontrol aplikasi tidak dapat sepenuhnya mencegah penyalahgunaan.
  • Push notification bukan sumber kebenaran. Aplikasi harus tetap refetch data dari backend ketika user membuka halaman terkait.

18. Incident Response

Ketika terjadi indikasi insiden, prosedur yang tersedia secara sistemik adalah:

  1. Bekukan transaksi wallet melalui freeze switch jika ada mismatch ledger, kecurigaan double spend, atau anomali kritis.
  2. Jalankan wallet reconciliation dan ledger integrity check.
  3. Review wallet_risk_events, wallet_disputes, wallet_audit_logs, dan ops.finance_audit_events.
  4. Nonaktifkan FCM device/token yang salah atau dicurigai.
  5. Revoke/suspend perangkat kantin bila public key mismatch atau perangkat tidak sah.
  6. Review Midtrans webhook log dan reconciliation queue untuk order yang tidak sinkron.
  7. Gunakan notification archive untuk investigasi historis tanpa memenuhi antrean aktif.
  8. Catat kejadian pada incident playbook dan backend alert agar tindak lanjut dapat diaudit.

19. Compliance Readiness

Sistem sudah memiliki pondasi untuk kesiapan produksi:

  • Kontrol akses berbasis RLS dan role.
  • Audit trail untuk perubahan finansial.
  • Webhook payment dengan signature verification.
  • Enkripsi lokal untuk cache dan key material tertentu.
  • Chat E2EE tanpa plaintext server untuk pesan baru.
  • Operasi wallet dengan signature, PIN verifier, risk rules, reconciliation, dan freeze switch.
  • Retensi notifikasi dengan arsip internal.
  • Health snapshot, incident playbook, dan security audit center.

Untuk produksi final, disarankan menutup residual risk advisor secara bertahap, menyiapkan SOP rotasi key/certificate pin, mengaktifkan leaked password protection jika memungkinkan, serta menjalankan test RLS dan payment reconciliation sebelum demo produksi.

20. Kesimpulan

Keamanan Al-Hasanah Media bukan sekadar enkripsi satu modul, melainkan kombinasi kontrol Android, database, Edge Function, payment gateway, notification pipeline, audit log, dan cron operasional. Klaim yang tepat untuk sistem ini adalah defense-in-depth dengan cryptographic enforcement pada area kritis, bukan klaim absolut bahwa seluruh server atau admin tidak pernah bisa memengaruhi data.

Dengan model ini, data wali santri dilindungi oleh RLS dan relasi kepemilikan, chat alumni dilindungi E2EE, finansial dikunci oleh backend online authority dan audit trail, dompet santri diperkuat oleh Ed25519, Argon2id, idempotency, nonce, risk rules, reconciliation, dan freeze switch, sementara operasional dipantau dengan archive, health snapshot, incident playbook, dan security audit center.
